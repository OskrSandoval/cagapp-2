- (decision) Stack conocido por el usuario: React + Vite (frontend), Node (backend), Supabase (DB/auth). Prioridad: simplicidad sobre escalabilidad (proyecto de aprendizaje, principiante)
- (decision) Limite frontend/backend: opcion B (hibrido) elegida. El frontend (React) usa el SDK de Supabase directamente SOLO para login/sesion (auth delegado a Supabase). Toda la logica de negocio (check-in con radio de 150m, busqueda de duplicados 1.5km, recalculo de promedio de calificaciones, crear/leer baños) pasa por la API propia de Node, que usa Supabase (con service role key) para persistir. El frontend nunca llama a Supabase para datos de negocio, solo para auth
- (decision) Framework de backend: Express.js. Se le presento al usuario la alternativa Next.js (full-stack unificado) pero se descarto porque va en contra del objetivo explicito de aprender backend como disciplina separada; se verifico con busqueda web que Express es la opcion mas alineada a ese objetivo de aprendizaje
- (decision) Paradigma de diseño para el backend: Arquitectura en Capas (Layered) - rutas -> controladores -> servicios (logica de negocio) -> acceso a datos (Supabase). Elegido por simplicidad y porque es el patron mas enseñado para Express
- (decision) Modelo de calificaciones: una sola tabla append-only (check_ins/calificaciones), nunca se actualiza ni borra. El promedio y la 'calificacion vigente' por usuario se calculan al leer (query que toma la fila mas reciente por par usuario-baño), no se mantiene una tabla de estado cacheado separada. Elegido por el usuario sobre la alternativa de tabla de estado actual + historial separados
- (decision) Convencion de nombres: español en todo el codigo (tablas de base de datos, nombres de variables, endpoints de la API) - consistente con el Glosario del PRD/UX (Baño, Calificacion, Check-in, Usuario)
- (decision) Calculo de distancias: formula Haversine en codigo de Node (JavaScript puro), sin PostGIS. Lat/lng se guardan como numeros normales en Postgres/Supabase. Elegido por simplicidad dado la escala del proyecto (CDMX, cientos de baños)
- (decision) Despliegue: backend Node/Express en Render (plan gratis, sin tarjeta, duerme tras 15min inactivo - aceptable para proyecto de aprendizaje con poco trafico). Frontend React/Vite en Vercel (build estatico, plan gratis). Base de datos/Auth ya en Supabase (nube). Se investigo en la web que Railway y Fly.io ya no tienen planes gratis reales sin tarjeta en 2026
- (decision) Autenticacion entre frontend y backend: JWT de Supabase enviado como Authorization Bearer token en cada peticion a la API de Node; Node lo verifica contra Supabase para identificar al usuario. Forma de respuestas de la API: REST simple, recurso directo en JSON + codigos HTTP estandar, errores como {error: mensaje}, sin envoltorios complejos
- (version) Versiones verificadas via web (septiembre 2026): React 19.3, Vite ~7.x (verificar al instalar, fuentes con datos conflictivos sobre si ya existe 8.x), Express 5.2.1, Node.js LTS 22+ (Node 20 llego a EOL abril 2026), @supabase/supabase-js 2.116.0
- (decision) Correccion de versiones tras verificacion web mas profunda: Vite es realmente 8.x (8.3.0 actual, no 7.x como se penso inicialmente). Node.js recomendado ahora es 24 LTS (Active LTS), no 22 (que ya es Maintenance LTS, no Active)
- (decision) Row Level Security (RLS): se habilita en las tablas de negocio (baños, calificaciones, perfiles) con politica deny-by-default (sin policies publicas). El backend usa la service role key que ignora RLS; RLS existe como defensa en profundidad por si la anon key llegara a exponerse. Resuelve ambiguedad detectada por revision adversarial
- (decision) Creacion del perfil de usuario: el frontend hace signup con Supabase Auth, y luego llama a un endpoint propio del backend (POST /perfiles, autenticado) para crear la fila de perfil con nombre_para_mostrar - no se usa un trigger de base de datos, para mantener la creacion de datos de negocio consistente con AD-1 (todo pasa por el backend)
- (decision) Desempate de 'calificacion vigente' (AD-3): se agrega columna bigserial 'secuencia' ademas del uuid id en calificaciones; el query usa ORDER BY created_at DESC, secuencia DESC LIMIT 1 para desempatar timestamps identicos de forma deterministica
- (decision) Forma publica de FR-12 (lista de calificaciones de otros usuarios): solo expone {nombre_para_mostrar, estrellas, created_at} - nunca usuario_id ni otro identificador interno. Perfil (FR-11, vista privada del propio usuario) puede incluir mas detalle porque es su propia data
- (decision) Politica de contraseñas y expiracion de sesion/JWT (FR-1, FR-2): delegadas completamente a los valores por defecto de Supabase Auth, no reimplementadas en el backend - consistente con AD-5 (Supabase Auth es la unica fuente de identidad)
- (decision) FR-9 precision de GPS insuficiente: el frontend envia {lat, lng, accuracy} (accuracy del Geolocation API del navegador) en cada intento de check-in. El backend distingue 'fuera de rango' (fuera de 150m aun considerando el accuracy reportado) de 'precision insuficiente' (el accuracy es tan malo que no se puede confirmar ni rechazar con certeza, ej. accuracy > 100m) y responde con codigos de error distintos para que el frontend ofrezca reintentar en el segundo caso
- (decision) FR-4 fallback de zona: se agrega campo de texto 'zona' a la tabla baños (ej. colonia/barrio) capturado al crear el baño; la busqueda por nombre de zona cuando se niega la geolocalizacion hace un filtro simple (ILIKE) sobre nombre y zona, sin geocodificacion
- (decision) Manejo de secretos: la service role key de Supabase y otras credenciales viven en variables de entorno (.env local, variables de entorno de Render/Vercel en produccion), nunca en el repositorio (.gitignore incluye .env)
- (decision) Reconciliacion NFR de carga <3s vs cold-start de Render (realista 30-60s tras 15min inactivo, no 'unos segundos' como se penso): se acepta como tradeoff conocido del plan gratuito para la etapa de aprendizaje - el objetivo de <3s aplica a peticiones con el servicio ya despierto; un ping periodico para mantenerlo despierto se difiere (ver Deferred)
- (decision) AD-4 aclarada: Haversine vive en una sola funcion compartida en la capa de servicios, usada tanto por FR-7 (radio 1.5km) como FR-9 (radio 150m), con la misma logica de redondeo, para que ambos calculos nunca puedan divergir
- (event) 4 revisiones completadas (rubric, verificacion web, reconciliacion contra PRD/UX/brief, adversarial) con 2 criticos/altos + varios medios/bajos entre todas. Todos corregidos: 6 ADs nuevos agregados (AD-8 a AD-13), 2 ADs reordenados para mantener numeracion ascendente, versiones de Vite/Node corregidas, ERD actualizado con tabla perfiles separada y campo zona, seccion de secretos y pruebas agregada a Consistency Conventions, tradeoff de cold-start de Render reconciliado explicitamente contra el NFR de <3s. Lint mecanico limpio (0 hallazgos)
- (event) spine finalized
