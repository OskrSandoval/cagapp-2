# Adversarial Review — CagApp 2.0

## Overall verdict

The spine is solid on layering and API shape but leaves four paradigm-level decisions unstated, each of which lets two ADs-compliant builders produce genuinely incompatible or unsafe systems. The worst gap is that AD-1 constrains frontend *code discipline* but never mandates Postgres Row-Level Security, and Supabase auto-exposes every table over PostgREST with the public anon key — a builder who takes AD-1 literally can ship a backend that is "correct" while the database itself is wide open. The other three gaps (tie-breaking on "most recent" row, who creates/owns the `usuarios` extension row, and public-vs-private shape of the `calificaciones` resource) are narrower but each breaks integration or leaks data in a concrete, reproducible way.

### Findings

- **critical** Builder A enables RLS on `baños`/`calificaciones` with owner-based policies, believing it protects against unauthorized writes; Builder B enables no RLS at all, believing the Express layer (AD-2) is the sole guard. Both are literally compliant with AD-1 ("el backend es el único que usa la service role key"). Neither is actually safe: Supabase's service role always bypasses RLS (so Builder A's policies never protect anything against the backend's own bugs), and Supabase auto-generates a public PostgREST endpoint over every table reachable with the anon key — so Builder B's "no RLS, Express is enough" leaves `baños` and `calificaciones` directly readable/writable by anyone holding the (public, frontend-embedded) anon key, completely bypassing AD-2/AD-3/AD-4/AD-7. AD-1 talks about which *code path* the frontend uses, not what the database itself exposes. *Fix:* Add an AD that mandates RLS `ENABLE` + deny-by-default (`USING (false)`) policies on every business table regardless of the service-role bypass, explicitly framed as "defense against Supabase's own auto-exposed REST API," and states that authorization/ownership checks (e.g., `creado_por` on `baños`) are enforced exclusively in the servicio layer — RLS is a network-exposure fence, not an authorization mechanism for backend logic.

- **high** The ERD says `USUARIOS` "extends" Supabase Auth's user table but the spine never states who creates that row or when. Builder A assumes a Postgres trigger on `auth.users` inserts the `usuarios` row (with `id = auth.users.id`) at signup, populating `nombre_para_mostrar` from signup metadata. Builder B assumes no trigger exists and has the backend lazily `INSERT ... ON CONFLICT` a `usuarios` row on first protected request, with `nombre_para_mostrar` supplied later via a `PUT /usuarios/mi-perfil` call. If Builder A's trigger runs first, Builder B's plain (non-upserting) insert throws a PK violation; if neither builder implements a trigger, rows created by "lazy backend insert" under concurrent double-requests race on the same PK; and either way `nombre_para_mostrar` chosen at signup time can end up silently discarded in whichever storage location the other builder's read path doesn't check. AD-1 also creates a genuine textual contradiction here: `nombre_para_mostrar` is a "perfil" field the rule explicitly routes through the Node API ("perfil ... se lee o escribe exclusivamente vía la API de Node"), yet it is captured during "registro," which the same rule allows straight to Supabase — so a builder can defensibly put it in `auth.signUp()`'s `user_metadata` (registro path) or defensibly refuse to and force a second API call (perfil path). *Fix:* Add an AD naming the exact creation mechanism (e.g., "a Postgres trigger `on_auth_user_created` inserts into `public.usuarios` with `id = new.id`; `nombre_para_mostrar` is set only via `PATCH /usuarios/mi-perfil` through the backend, never via Supabase `user_metadata`") and state explicitly that `usuarios.id` is a 1:1 FK to `auth.users.id`, not merely "the same UUID by convention."

- **high** AD-3 says vigente/promedio is computed by "reading the most recent row per (usuario_id, baño_id)" but specifies no tie-break for identical `created_at` timestamps (realistic on a fast double-submit/network retry of a check-in). Builder A implements this as `ORDER BY created_at DESC LIMIT 1` (no secondary sort key) — Postgres does not guarantee which of two tied rows this returns, and the choice can differ from run to run as the table is vacuumed/reindexed. Builder B implements it as a `MAX(created_at)` correlated subquery — which, on a tie, returns *both* rows, not one, silently breaking the "single most recent row" contract and, if fed directly into an AD-7 "bare resource" response, returns an array where every other caller expects an object. Because the two tied rows can carry different `estrellas` values (e.g., a user double-taps 3★ then 5★ in the same request burst), the two implementations can report a different vigente rating for the same user on the same baño, and therefore a different public average. *Fix:* Tighten AD-3 to specify a deterministic tie-break, e.g. "most recent row per (usuario_id, baño_id), ordered by `created_at DESC, id DESC`, taking exactly one row," and require the query pattern to be a single service function shared by every caller (FR-9/FR-10/FR-12), not reimplemented per endpoint.

- **medium** AD-7 says success responses are "el recurso directo" using the DB's literal Spanish column names (AD-6). Applied literally to FR-12's public, unauthenticated ratings list, this means returning raw `calificaciones` rows including `usuario_id` — a stable UUID equal to the person's `auth.users.id` — to anonymous visitors. Builder A (owns FR-12) does exactly this, treating "the resource" as the raw table row per AD-6/AD-7. Builder B (owns FR-11 Perfil, and reuses the same underlying `obtenerCalificaciones` service for consistency) reshapes the object to substitute `nombre_para_mostrar` for `usuario_id` before returning it publicly, since Perfil's private context is where the raw user linkage is legitimate. Now "the calificación resource" has two incompatible public JSON shapes depending on which builder's endpoint you hit, and Builder A's version incidentally creates a pseudonymous cross-baño tracking vector for any anonymous visitor (correlate one `usuario_id` across every rating it ever made, city-wide) — a real, if minor, privacy leak the spine never rules out. *Fix:* Add a convention that public (unauthenticated) endpoints project a distinct "display shape" for `calificaciones` (no raw `usuario_id`/FK columns; use `nombre_para_mostrar` or an opaque per-rating id instead), separate from the internal/authenticated shape used by Perfil and the check-in write path, and name both shapes explicitly so they aren't accidentally unified into one "the resource" contract.

- **low** The Structural Seed lists `servicios/` as owning "geolocalizacion, deduplicacion, promedios" but AD-4 only binds the distance/Haversine calculation to "la capa de servicios," not to a single named module. Nothing stops Builder A from implementing check-in-radius (150m, FR-9) and search-radius (1.5km, FR-7) as two separate Haversine call sites with independently rounded/truncated results (e.g., one rounds distance to meters before comparison, one doesn't), which is still "one implementation of the formula" per AD-4's letter but produces boundary-case disagreements (a check-in at exactly 150.0m rounds differently than a listing at exactly 1.5km). *Fix:* Tighten AD-4 to require one shared `calcularDistancia`/`estaEnRadio` function used by both call sites, with rounding/comparison semantics (e.g., `<=` vs `<`) specified once.
