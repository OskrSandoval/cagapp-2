# Architecture Spine Review — CagApp 2.0

## Overall verdict

This is a solid, well-calibrated spine for a beginner learning project: the seven ADs cover the highest-value divergence points (frontend/backend boundary, layering, append-only ratings, single Haversine location, identity, naming, API shape), all are concrete and largely enforceable, the Deferred list is genuinely safe to leave open, the stack table's versions are traceable to the memlog's web-verification entry, both Mermaid diagrams are valid and substantive, and no template placeholders survived. The main weaknesses are a few explicit PRD hand-offs to architecture that never got resolved or even mentioned (GPS-accuracy retry behavior, session length, password policy) and total silence on secrets/env management and testing strategy — both worth a line each even at this project's low-rigor stakes.

### Findings

- **high** FR-9's GPS-accuracy/retry behavior — which the PRD explicitly punts to architecture ("`[SUPUESTO: mecanismo exacto de reintento/tolerancia por precisión de GPS queda para arquitectura]`" and repeated in PRD §9 Índice de Supuestos) — is never mentioned anywhere in the spine, not even in Deferred (ARCHITECTURE-SPINE.md, AD-4 / Deferred section). This is real app logic (accuracy threshold, retry UI, which layer decides "GPS not precise enough") that two builders could implement completely differently, directly affecting whether check-ins near the 150m/1.5km boundaries succeed. *Fix:* Add a short AD or a Deferred entry with an explicit interim rule, e.g. "backend rejects/retries when device-reported accuracy exceeds Xm; no client-side override," even if the exact threshold is picked at build time.

- **high** Secrets/environment management is completely silent: the doc states the backend "es el único que usa la `service role key`" (AD-1, AD-5) but never says how that key (or any Supabase URL/anon key) reaches the Render service or local dev, whether it's committed, or how dev vs. prod projects are configured (ARCHITECTURE-SPINE.md, Deployment & Environments section). For a project whose entire security model rests on the service role key never leaking, this is a real operational envelope item the checklist calls out by name and it isn't decided, deferred, or flagged as an open question anywhere. *Fix:* Add one line to Deployment & Environments, e.g. "service role key and Supabase URL live in `.env` (gitignored) locally and in Render/Vercel's environment-variable dashboards in prod; never committed."

- **medium** Testing strategy is entirely absent from the document — not decided, not deferred, not an open question. The checklist explicitly treats "silence is not fine" even for "no tests for now" as a valid answer. *Fix:* Add a one-line Deferred entry, e.g. "No automated tests in MVP scope — learning-project priority is shipping the layered structure; revisit if regressions start costing more than tests would."

- **low** AD-6 ("vocabulario en español en todo el código... sin sinónimos ni traducciones parciales") doesn't carve out an exception for generic/structural fields, yet the document's own ER diagram uses `created_at` (English) rather than a Spanish equivalent like `creado_en` (ARCHITECTURE-SPINE.md lines 75-79 vs. 130/139/146). As written, the rule and the example contradict each other, leaving room for one builder to Hispanicize timestamp/id columns and another to follow the ERD's English convention. *Fix:* Add a clause to AD-6's Rule exempting generic structural columns (`id`, `created_at`, `updated_at`) from the Spanish-only mandate, matching the ERD.

- **low** Two smaller PRD-to-architecture hand-offs are left unaddressed: password minimum-length policy (PRD §9, FR-1) and session/JWT expiration period (PRD FR-2: "hasta que expira el periodo definido por arquitectura"). Divergence risk here is low since both are effectively delegated to Supabase Auth's own defaults via AD-5, but the spine never says so explicitly. *Fix:* One clause in AD-5's Rule or the Consistency Conventions table — "password policy and session/token lifetime are Supabase Auth project defaults, not custom code" — closes the loop cheaply.

- **low** Error-handling conventions are only partially covered: AD-7 fixes the wire format (`{error: string}` + HTTP code) but not which layer decides which status code (validation vs. not-found vs. auth vs. unexpected-error), leaving room for inconsistent mapping across controllers. Given the project's stakes, this is minor and arguably acceptable to leave implicit, but worth a one-line convention if it starts causing inconsistency in practice.
