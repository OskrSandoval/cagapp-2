# Accessibility Review — CagApp 2.0

## Overall verdict

No WCAG/screen-reader target is stated in the PRD, and EXPERIENCE.md is honest about that rather than quietly inventing a compliance claim — the right call for a hobby-to-real-launch consumer app. The proposed "light floor" is directionally reasonable, but the actual hex values in DESIGN.md's token block produce several concrete WCAG AA text-contrast failures, and they land specifically on the highest-traffic elements in the whole product: every primary CTA button, every map pin badge, and the score/range chips — exactly the surfaces the product needs to be legible on in the outdoor-sunlight scenario EXPERIENCE.md itself calls out. None of this is expensive to fix (mostly darkening a token or two and adding `for`/`id`/`aria-label` attributes), so it's worth doing before launch even at hobby stakes. Tap-target sizing is mostly fine except for two real misses (back button, map pin badges) that undercut the design doc's own "already generously sized" claim.

### Findings

- **high** `primary` (`#FF5A36`) as text/label color against `bg`/`surface`, and `primary-ink` (white) text against a `primary` fill, both measure ≈3.1:1 — below the 4.5:1 AA threshold for normal-size text (only large-text/UI-component 3:1 is met). This is the single most-used color pairing in the app: every full-width primary button label ("Entrar y encontrar baño 💩", "Hacer check-in aquí", "Confirmar calificación 🚀"), the FAB label, the segmented-tab active label, and the rate-caption pill all use it at 13–15px bold, none of which qualify as "large text" under WCAG (needs ≥18.66px bold). *Fix:* darken `primary` by ~10-15% luminance for **text-bearing** uses only (a `primary-text` variant), or keep `primary` as the fill and darken `primary-ink`'s surrounding treatment isn't the lever — the fill itself needs to darken. A ~10% darker orange (check against both white text and white background) gets this to ~4.5:1 without changing the brand's hue.
- **high** Map pin badges (`.pin .badge`) render white text on `success`/`primary`/`warning` fills at 11px bold — measured contrast is ~3.4:1 (success), ~3.1:1 (primary/mid), ~4.35:1 (warning), all below the 4.5:1 small-text AA threshold (`DESIGN.md` § Components, `map-pin`). This is the screen where misreading a number has the most direct product cost (choosing the best nearby bathroom, in bright outdoor light, among several close-together pins). *Fix:* same as above — darken `success` and `primary` slightly for this use, or increase badge text weight/size marginally; `warning` is close enough that a small tweak clears the bar.
- **medium** `success` (`#2E9E5B`) as text color on `success-surface` (`#E6F4EB`) measures ≈3.0:1 — used in the score-tag ("4.5 ⭐ — ¡una joya!") and the in-range chip ("✅ Estás a tiro de piedra…") at 12-12.5px bold (`key-detalle-checkin.html` `.score-tag`, `.range-ok`). Also `muted` on `success-surface` (the check-in banner's helper line, `.checkin-banner span`) measures ≈4.31:1, a near-miss just under 4.5:1. *Fix:* darken `success` slightly for text use, or increase `success-surface` lightness/reduce its green tint — either alone likely clears both instances since they share the same surface token.
- **medium** Map pin badges are ~19px tall (`padding: 3px 9px` + 11px font, no larger touch buffer) — below even the WCAG 2.5.8 AA minimum target size (24×24 CSS px), let alone the "≈44×44, generously sized" claim EXPERIENCE.md makes for the mockups generally. This is on the busiest, most tap-dense screen (multiple pins close together on Mapa). *Fix:* add invisible padding/hit-area around the badge (e.g. a transparent `::before` or larger clickable wrapper) without growing the visual pill.
- **medium** Back button (`.nav .back` in `key-detalle-checkin.html`) is 32×32px — smaller than the profile icon (42px) and well under the 44px comfortable floor the design doc claims is already held everywhere. It's also the *only* way back on the Detalle/Check-in screen and sits in the top-left corner, the hardest one-handed mobile thumb-reach zone. *Fix:* bump to ~40-44px, matching `.profile-btn`.
- **medium** Login/Registro `<label>` elements have no `for` attribute and inputs have no matching `id` (`key-login.html` `.field label` / `.field input`) — visually the labels look correctly associated, but a screen reader has no programmatic link between them, and clicking a label won't focus its input. Cheap, high-value fix that should also apply to the not-yet-mocked Crear Baño form. *Fix:* add `id` to each input and `for` to its label (or wrap the input inside the `<label>`).
- **medium** Icon-only controls have no accessible name: `.profile-btn` (just "👤") and `.nav .back` (just "←") rely entirely on a symbol a screen reader may announce ambiguously or not at all. The FAB and Mapa/Lista toggle are fine — both pair an icon with real label text. *Fix:* add `aria-label="Perfil"` and `aria-label="Volver"` respectively.
- **low** Login password field is `<input type="text" placeholder="••••••••">` in the mock (`key-login.html` line 284), not `type="password"`. It's a static mockup so this doesn't matter for the deliverable itself, but the file is listed as a build reference and could get copy-pasted verbatim. *Fix:* note in build handoff that the real input must be `type="password"` with an autocomplete hint (`current-password` / `new-password`).
- **low** Star picker (`key-detalle-checkin.html` `.star-picker`) has no per-star accessible semantics specified anywhere (not in the mock, not in EXPERIENCE.md's Component Patterns) for what is the app's single most important input — the rating itself. Visual tap targets (34px, `gap:8px`) are close to but not quite the 44px comfortable floor, and nothing besides font-glyph size defines the actual hit box. *Fix:* at build time, implement as 5 real buttons/radios with `aria-label="Calificar N de 5"` and explicit padding around each glyph to guarantee a ≥44px hit area, not just a 34px glyph.
- **low** `muted` (`#8A6A5A`) on `bg`/`surface` measures ~4.9:1 / ~4.66:1 — both pass AA today but with very little margin, and `muted` is used at the smallest sizes in the system (11-12.5px captions, fine print, street labels). *Fix:* no change needed now, but flag as a token not to lighten further, and re-check if it's ever used at reduced opacity or over a busier/lighter background (e.g. the translucent white street-label chips on the map, which sit over variable green map tiles and weren't independently verified here).
- **low** Color-only encoding on map pins (`success`/`primary`/`warning` tiers) is already self-flagged in EXPERIENCE.md as partially-mitigated by the co-present numeric text ("🚽 4.5★") — that mitigation is correct in principle (the actual number is more informative than a tier label would be), but its effectiveness is currently undercut by the same contrast failure noted above: if the white text on the badge is hard to read, the redundant channel isn't actually usable. Fixing the pin-badge contrast finding above resolves both issues together.
- **low** Profile icon is 42×42px vs. the "≈44×44" figure EXPERIENCE.md cites for it — functionally a non-issue (both are comfortably above the 24×24 AA minimum) but worth a one-line correction so the design doc's stated sizes match the mock exactly.
- **informational** Reduced motion, focus order, and full screen-reader labeling remain genuinely unspecified, as EXPERIENCE.md already discloses — agreed this is fine to leave open pre-launch given no stated compliance target, with one addition: DESIGN.md's own `[GAP]` on tablet/desktop reflow means keyboard-only access to map pins will eventually need a real answer (not just touch), since a fluid reflow to a wider viewport doesn't remove the keyboard-navigation question the way a touch-only mobile web app can mostly defer it.
